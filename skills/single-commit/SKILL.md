# Single Commit Workflow Skill

## 목적
피싱로그 저장소에서 하나의 사용자 요청을 처리할 때 여러 파일이 수정되더라도 **최종 커밋은 반드시 1회만 생성**한다.

## 적용 범위
- 저장소: `EUNneun/fishing_log`
- 기능 추가
- 버그 수정
- UI 수정
- 리팩터링
- 여러 파일 생성/수정이 필요한 모든 작업

## 핵심 원칙
1. 사용자 요청 1건 = 커밋 1건.
2. 같은 작업에서 `create_file`, `update_file`을 파일마다 바로 실행하지 않는다.
3. 먼저 필요한 모든 파일을 읽고 변경 계획을 확정한다.
4. 수정할 파일 내용을 모두 메모리에서 완성한 뒤 한 번의 Git 작업으로 묶는다.
5. 중간 저장용 커밋, 임시 커밋, 파일별 커밋을 만들지 않는다.
6. GitHub Pages 배포가 커밋마다 실행되므로 불필요한 배포를 만들지 않는다.

## 작업 절차
### 1. 사전 조사
- 변경 대상 파일을 모두 조회한다.
- 새 파일이 필요한지 확인한다.
- 기존 코드와 충돌 여부를 확인한다.
- 사용자 요청을 완료하기 위해 필요한 전체 변경 범위를 먼저 확정한다.

### 2. 변경안 작성
- 수정 파일 전체의 최종 내용을 메모리에서 준비한다.
- 새 파일도 최종 내용까지 준비한다.
- 파일 A를 수정한 뒤 커밋하고 파일 B를 수정하는 방식은 금지한다.

### 3. 단일 커밋 실행
가능하면 Git tree/commit API를 사용해 여러 파일을 한 커밋으로 작성한다.

권장 방식:
- 필요한 blob 생성
- 하나의 tree 생성
- 하나의 commit 생성
- branch ref를 마지막에 한 번만 update

### 4. 예외
다음 경우에만 추가 커밋을 허용한다.
- 첫 커밋이 실패하여 저장소에 반영되지 않은 경우
- 사용자가 첫 커밋 이후 새로운 변경을 추가 요청한 경우
- 긴급 복구가 필요한 경우

단순 실수 수정이나 누락 보완을 이유로 같은 요청 안에서 추가 커밋을 만들지 않는다. 커밋 전에 검토한다.

## 커밋 전 체크리스트
- [ ] 이 요청에서 수정할 파일을 모두 확인했는가?
- [ ] 새 파일/기존 파일 변경을 모두 한 번에 준비했는가?
- [ ] 컴포넌트 import 누락이 없는가?
- [ ] 타입 변경 시 관련 사용처를 모두 수정했는가?
- [ ] 라우트 추가 시 링크/진입점까지 같이 수정했는가?
- [ ] 로컬 저장 구조 변경 시 읽기/쓰기 양쪽을 같이 수정했는가?
- [ ] UI 변경 시 모바일/PWA에서 깨질 가능성을 확인했는가?
- [ ] 최종 커밋이 1회만 생성되는가?

## 사용자에게 보고
작업 완료 시 아래 형식으로 간단히 보고한다.

- 적용 내용 요약
- 최종 커밋 SHA
- "이번 작업은 단일 커밋으로 반영했습니다." 문구

## 금지 예시
잘못된 방식:
1. 새 파일 생성 → 커밋 A
2. 기존 파일 수정 → 커밋 B
3. 누락 수정 → 커밋 C

올바른 방식:
1. 전체 파일 조사
2. 전체 변경 준비
3. 모든 변경을 하나의 tree에 포함
4. 커밋 A 한 번 생성
5. branch ref 한 번 갱신

## 우선순위
이 규칙은 빠른 작업보다 우선한다.
여러 파일을 순차적으로 커밋하는 것보다 작업 시작 전에 전체 변경 범위를 파악하는 것을 우선한다.
